# LRS code, phase 1 of the resubmission (2026-10-02)

What was found and changed so that every number of the LRS paper's Sections 3 and 4 can be produced by
this repository. Companion to [`cleanup-2026-09-26.md`](cleanup-2026-09-26.md) and
[`logistic-regression-status-2026-09-17.md`](logistic-regression-status-2026-09-17.md).

## 1. The visual metric: why the published F1 values did not reproduce, and the fix

- **Cause.** The published run (2024-10) drew geometries with `SqlSpatialToGdiBitmap.ParseSqlGeometry`, which
  never set `Graphics.SmoothingMode`, so lines were aliased (GDI+ default). Since the 2025 restructuring the
  metric went through the map renderer (`VectorLayer.AsGdiBitmapAsync` → `GdiBitmapRenderStrategy`), which
  sets `SmoothingMode.AntiAlias`. Because the metric counts every non-transparent pixel as drawn, an
  anti-aliased 1-px line covers about twice as many pixels (median 2.1× on the 348 published features).
- **Fix.** `Infrastructure.GdiPlus/IO/MetricRasterizer.cs`: the metric draws with its own rasterizer and
  `MetricRenderOptions` (pen width, anti-aliasing), no longer with the map renderer.
  `SimplificationHelper.RenderOptions` (default `MetricRenderOptions.Published`, aliased 1 px) is used by every
  research driver (`SimplificationHelper.RenderForMetric`, `GeneralHelper.Render`) and by the oracle labeller.
  Every run folder now gets a `Rendering.txt`.
- **Check** (`--run ReproducePublishedMetric`, `PublishedMetricReproduction`, run
  `4. Paper2\AlgorithmRun\2026-10-02-ReproducePublishedMetric`): 348 features × 4 baselines × 3 coefficients =
  4,176 rows; simplified point count equal in 4,174, TP/FP/FN equal in 4,169 when the reference raster is drawn
  from all sampled features of the layer, as the published driver did. With the feature alone (the corrected
  protocol of 2026-09-26) 3,989 rows are equal; the rest differ by the neighbours' pixels.
- The runs of 2026-09-28 (`RevisionPublishedFeatures128`, `RevisionOracle128`) and the first oracle file were
  made with the anti-aliased rendering; their F1 values are not comparable with the published ones.

## 2. Where the coefficients of the manuscript come from

- **Models used in the published experiments** (LRSv4 = LR4v23, LRSv7 = LR7v23): the 2024 gradient-descent
  trainer (β₀ = 1, rate 0.1, 5,000 iterations, not converged) on the V23 synthetic set (4,182 triads, bases
  0.5–32 px). The trainer is kept in `tests/.../MachineLearning/Published/PublishedGradientDescentLogisticRegression.cs`
  and `PublishedCoefficientsTest` reproduces its coefficients from `SyntheticDataFactory` alone.
- **Coefficients and metrics printed in Tables 4 and 5 of the manuscript** (v10–v12): not from the C# code.
  scikit-learn `LogisticRegression(penalty="l1", solver="liblinear", C=1)` on standardized features, fitted on all
  rows of `4. Paper2\Model\Model-All-7Feature.csv` (1,328 triads exported on 2024-09-11: bases 0.5–4 px only, no
  collinear rows, an earlier label version), gives 8.254, −4.040, 0.883, 3.241, 3.241, 1.882, −1.821 against the
  printed 8.246, −4.038, 0.881, 3.240, 3.240, 1.879, −1.81; its 5-fold cross-validation (0.910 for seven features,
  0.925 for the four of `Model-All-4Feature.csv`) is the "0.90 and 0.92" of the text. The printed test metrics
  (accuracy 0.9398 …) come from a split that could not be identified. So the tables describe a different data set
  and trainer than the models the experiments ran.
- **From now on**: `--run ModelSelection` (`ModelSelectionExperiment`) writes every number of those tables from
  the training set the models use, with the library trainer (proximal Newton, L1, converged), seed 2026.

## 3. Model selection on the V23 set (run `2026-10-02-ModelSelection`)

- No label conflicts (0 of 4,182 triads share a feature vector with the opposite label).
- Ranking by the size of the standardized L1 coefficients at λ = 1: BaseLength, Area, DistanceToPrevious,
  DistanceToNext, SquareCosineOfAngle, VerticalDistance, CosineOfAngle. The top four are exactly the published
  LRSv4 set. Ranking by entry into the L1 path is different (VerticalDistance first) and its top four is worse
  (CV accuracy 0.911).
- λ by 5-fold CV with the one-standard-error rule: λ = 1 for seven features (best 0.1; accuracies flat for λ ≤ 1),
  λ = 3 for four features. CV accuracy at λ = 1: 0.948 (seven) and 0.946 (four), i.e. the two models are equally
  good once the trainer converges.
- Stratified 80/20 split (3,346 / 836 triads), λ = 1, label 1 = retained: LRSv7 accuracy 0.949, precision 0.964,
  recall 0.974, F1 0.969; LRSv4 0.951, 0.968, 0.973, 0.970.

## 7. E1: labels copied from RDP (phase 2, run `2026-10-02-E1RdpLabels`)

37,243 triads from 350 OSM features labelled by RDP at 1 px (24 % kept). CV accuracy 0.916, but recall of the
kept points only 0.74; conflicts 0.9 % at 0.1 rounding (synthetic 0 %). On the 348 published features the
RDP-trained models lose F1 against the synthetically trained ones (median 0.831 vs 0.876 for seven features,
Wilcoxon p = 4·10⁻¹⁴) at slightly higher compression (0.456 vs 0.442), while RDP itself at that compression
(0.5 px) reaches 0.903. Details and figure: `4. Paper2\AlgorithmRun6-10-02-E1RdpLabels\E1-summary.md`.

## 8. Li–Openshaw added to the library (2026-10-02, not used)

`Simplifications.SimplifyByLiOpenshaw` (vector mode: circular SVO of diameter `DistanceThreshold` centred at the
entry point, midpoint of entry and exit retained) and `SimplifyByLiOpenshawRaster` (raster mode: square cells of side
`DistanceThreshold`, a run of consecutive vertices in one cell becomes its centroid); `SimplificationType.LiOpenshaw`
("LO") and `LiOpenshawRaster` ("LOR"), dispatched by `Geometry.Simplify`. Both generate new points (the result is not a
subsequence), so they cannot label LRS triads. Tests: `tests/.../Spatial/LiOpenshawTest.cs` (definition tests worked
out by hand; no reference implementation was available). Author's decision: in the library only, not in the
experiments or the manuscript.

## 10. Fused classifier evaluation (2026-10-04)

`LogisticSimplification.IsRetained(T first, T middle, T last)`: the coordinates are read once, the model's features are
computed into a reused `double[]` with the formulas of `LRSimplificationParameters` (same operations, same order → the
same bits), and for a `LogisticRegression` the logit is formed in place in the order `Predict` uses; other classifiers
get the buffer as a list. The three traversals use it; the cumulative-area variant keeps the parameter object. Test
`FusedEvaluationTest` (19 cases) shows the simplifications are identical to the parameter-object path. Effect
in the Release micro-benchmark (100,000-point lines, library traversal): random walk 59 → 13.5 ms, sine 60 → 16 ms,
straight line 196 → 45 ms. Note that `dotnet run` builds the research project in Debug unless `-c Release` is given;
the E6 runs before 2026-10-04 were Debug builds, so their absolute times are 2–6× too high. `Timing-summary.txt`
now states the build configuration; `2026-10-02-E6Timing` is superseded.
